# Markdown 内容契约

## 1. 适用范围

本契约约束 `content/行业动态追踪.md` 的可解析格式。内容编辑者可以增加事实和分析，但不得随意改变以下标题、字段和日期口径。

## 2. 固定一级章节

一级章节必须使用中文序号、顿号和固定名称，并保持唯一：

```markdown
一、文档说明
二、总览
三、本期重点摘要
四、行业动态
五、产品动态
六、技术革新
七、竞品与标杆公司动态
八、公司内部进展
```

如果确需增加、删除或改名，应先修改本契约，再修改同步脚本、页面导航和测试。

## 3. 章节内标题

```markdown
## 二级标题
### 三级标题
#### 具体条目或能力名称
```

- `##` 和 `###` 自动进入章节内导航。
- `####` 只作为正文小标题，不进入章节内导航。
- 同一章节内标题应语义清晰，不使用“其他”“补充”等无法长期识别的名称。

### 文档说明示例

```markdown
一、文档说明
## 文档目的
## 服务对象
## 更新方式
## 覆盖时间
```

### 周期章节示例

第四至第七章按照最新周期在前排列：

```markdown
## 2026-09-01—2026-09-07
## 2026-08-24—2026-08-30
```

## 4. 日期规则

- 单日日期：`YYYY-MM-DD`，例如 `2026-09-07`。
- 时间范围：`YYYY-MM-DD—YYYY-MM-DD`，中间使用中文长横线 `—`。
- 覆盖时间正文可以使用 `YYYY年MM月DD日—YYYY年MM月DD日`。
- 发现日期、媒体发布时间和事件发生日期不等同时，应明确区分。

## 5. 本期重点摘要

重点摘要使用固定六列表格：

```markdown
| 事件 | 类型 | 关键词 | 一句话影响判断 | 来源 | 发布时间 |
|---|---|---|---|---|---|
| 示例事件 | 技术与模型 | ASR、评测 | 一句话判断 | 官方来源 | 2026-09-07 |
```

约束：

- 每行必须包含六列，不得缺列或交换顺序。
- `关键词` 使用顿号、中文逗号或英文逗号分隔。
- `发布时间` 使用 `YYYY-MM-DD`。
- `来源` 写可识别的机构或官方渠道；详细条目中尽量附一手链接。
- 只有达到本期优先关注门槛的事件才进入该表。

## 6. 详细事件条目

详细条目至少应提供事实、变化、能力、业务和行动五类价值中的两类；重点事件至少提供三类。推荐字段：

```markdown
#### 事件名称
判断状态：持续跟踪
标签：#ASR #家庭场景

1. 事实与变化：……
2. 核心机制或能力：……
3. 证据与边界：……
4. 对 OS 平台部的影响：……
5. 建议动作：……
6. 来源：https://example.com
发布时间：2026-09-07
核验状态：已核验 / 待核验
```

字段可以按事件价值适度删减，但不得省略事实来源和时间边界。

## 7. 公司内部进展

内部进展采用以下结构：

```markdown
八、公司内部进展

> 内容边界：内部状态以当前有效材料和责任团队确认为准。

## 已有技术能力（存量材料）
### 语音合成（TTS）
#### 具体能力名称

## 在研方向（待内部确认）
## 待补充的跟踪字段
```

每项内部能力建议记录：

- 信息来源；
- 确认日期；
- 责任团队；
- 当前阶段；
- 适用产品；
- 关键指标及测试条件；
- 依赖与风险；
- 下一步动作。

缺少当前有效内部依据时，必须标记“待内部确认”。外部材料不能直接证明公司内部能力状态。

## 8. 变更本契约

新增字段或调整格式时，必须同步完成：

1. 更新本文件；
2. 在 Markdown 中提供真实示例；
3. 修改 `scripts/sync-content.mjs`；
4. 修改页面展示和样式；
5. 增加或更新自动测试；
6. 在实际发布后更新 `CHANGELOG.md`。
