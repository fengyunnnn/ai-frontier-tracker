# Markdown 内容契约

## 1. 适用范围

本契约约束 `content/行业动态追踪.md` 的可解析格式。内容编辑者可以增加事实和分析，但不得随意改变以下标题、字段和日期口径。

## 2. 固定一级章节

一级章节必须使用中文序号、顿号和固定名称，并保持唯一：

```markdown
一、文档说明
二、总览
三、重点摘要
四、行业动态
五、产品动态
六、技术革新
七、竞品与标杆公司动态
八、公司内部进展
```

如果确需增加、删除或改名，应先修改本契约，再修改同步脚本、页面导航和测试。

## 3. 章节内标题

```markdown
## 二级标题
### 三级标题
#### 具体条目或能力名称
```

- `##` 和 `###` 自动进入章节内导航。
- `####` 只作为正文小标题，不进入章节内导航。
- 同一章节内标题应语义清晰，不使用“其他”“补充”等无法长期识别的名称。

### 文档说明示例

```markdown
一、文档说明
## 文档目的
## 服务对象
## 内容覆盖
## 更新方式
## 覆盖时间
```

`## 内容覆盖` 说明报告的主线范围与双轨制（轨道 A 交互体验与 AI 前沿战略雷达／轨道 B 业务落地与产业约束雷达）；`## 更新方式` 只保留日常扫描、周度整理、周期复盘、专题升级四项流程，不再夹带轨道说明。

**渲染约束（2026-09-14 起）**：引导句与分点列表之间必须留一个空行。`app/trend-explorer.tsx` 用 `marked` 解析正文，引导句与列表直接相邻时会被视为同一段，分点会连成一行。

### 周期章节示例

第四至第七章按照最新周期在前排列：

```markdown
## 2026-09-01—2026-09-07
## 2026-08-24—2026-08-30
```

### 总览结构

`二、总览` 当前的呈现方式是「一句话判断 + 三个事实层 + 一段优先级与行动判断」：先交代本期主线转向，再分能力、产品、产业三层给出事实判断，最后说明 平台团队应如何理解和应对。三个事实层以 `【层次名】` 起行，并以 `→ 对应章节：X` 收尾，指向承载该层证据的章节，方便读者跳转。

```markdown
二、总览
截至…，主线正在从“…”转向“…”。这个转变同时发生在能力、产品、产业三个层面：…
【能力层】…
→ 对应章节：六、技术革新
【产品层】…
→ 对应章节：五、产品动态、七、竞品与标杆公司动态
【产业层】…
→ 对应章节：四、行业动态
【团队优先级与行动判断】
…
1. Level 1｜生存层：准入与内容闭环
…
2. Level 2｜竞争层：自然交互与真实场景
…
3. Level 3｜未来层：任务编排与跨端智能
…
4. 横向诊断轴｜先归因，再投入
…
→ 对应章节：八、公司内部进展
```

说明：

- 层次名称、层次数量与 `→ 对应章节：` 归属标记属于**当前版本的叙事呈现**，可能随评审反馈调整；变更时直接改内容即可，**不设测试断言**，只在评审时人工核对，避免把可变叙事变成长期维护负担。
- `【团队优先级与行动判断】` 只讲优先级与投入判断，说明 平台团队应如何理解和应对前面的能力、产品、产业变化；它**不是**对已确认内部能力现状的陈述，内部能力现状以「八、公司内部进展」为准。
- 需要长期保持的硬约束：`1. Level 1｜生存层：准入与内容闭环`、`2. Level 2｜竞争层：自然交互与真实场景`、`3. Level 3｜未来层：任务编排与跨端智能`、`4. 横向诊断轴｜先归因，再投入` 四个编号判断条目必须保留；它们是页面「竞争判断分层」卡片（`report.directions`）的唯一数据源，编号必须为 1—4 且连续，每条编号行之后紧邻一行判断说明。
- **排版硬约束（2026-09-14 起）**：总览每一行之间都要留空行，即「一行一块」。总览没有 `##`/`###` 标题，`【层次名】` 行与 `→ 对应章节：X` 行靠空行分隔才各自成为独立块；相邻两行非空会被 `marked` 并进同一个段落，整章退回「挤成一坨」。`tests/governance.test.mjs` 的「总览正文以空行分块」测试会拦住这种回退。
- 编号判断的说明行需**缩进 3 个空格**（`1. ` 的 content indent）。缩进后说明仍是同一条目内的续段，四条判断保持一个 `<ol>`；不缩进会让空行把列表切成 4 个单条列表。缩进不影响 `directions` 提取——`sync-content.mjs` 与测试都按 `trim()` 后取「下一条非空行」。
- `【层次名】标题` 与 `→ 对应章节：X` 由 `app/trend-explorer.tsx` 渲染为分层小标题与章节指向标记（`overview-layer` / `overview-ref`），样式在 `app/globals.css` 的 `.markdown-overview` 作用域内。这是呈现层约定，改文案不需要动代码。
- 总览是判断，不是目录：`→ 对应章节：` 只做归属标注，不替代各章节正文。
- 总览不得只写运营商准入视角，它对应的是语音交互与 AI 人机交互的全景。

## 4. 日期规则

- 单日日期：`YYYY-MM-DD`，例如 `2026-09-07`。
- 时间范围：`YYYY-MM-DD—YYYY-MM-DD`，中间使用中文长横线 `—`。
- 覆盖时间正文可以使用 `YYYY年MM月DD日—YYYY年MM月DD日`。
- 发现日期、媒体发布时间和事件发生日期不等同时，应明确区分。

### 4.1 时间字段同步（每次更新必须连改）

页面顶部与正文里共有 5 处时间。**任何一次内容更新都必须让这 5 处互相一致**；改一处漏改其他处，页面就会出现「页头写着刚更新、正文还停在旧日期」的错配。

| # | 位置 | 格式 | 数据来源 | 维护方式 |
|---|---|---|---|---|
| 1 | 一、文档说明 → `## 覆盖时间` 正文 | `YYYY年MM月DD日—YYYY年MM月DD日`（**补零**） | `content/行业动态追踪.md` | **手改** |
| 2 | 页面页头「观察周期：」 | 与第 1 项逐字相同 | 同步脚本提取为 `report.coverage`，由 `app/trend-explorer.tsx` 渲染 | 自动（改第 1 项即同步） |
| 3 | 二、总览首个日期「截至YYYY年M月D日」 | 中文短格式（**不补零**） | `content/行业动态追踪.md` | **手改** |
| 4 | 三、重点摘要「本期周期：」＋四—七章周期标题 `## A—B` | `YYYY-MM-DD—YYYY-MM-DD` | `content/行业动态追踪.md` | **手改** |
| 5 | 页面页头「更新于 YYYY/MM/DD HH:mm」 | 页面格式化展示 | 内容源文件的 mtime（`report.sourceUpdatedAt`） | **自动，禁止手写** |

#### 时间字段同步清单（每次改动内容源必做）

编号同上表。改完内容源、落盘前逐项勾选：

- [ ] ① `## 覆盖时间` 正文 —— 中文长格式，月日**补零**（`2026年08月01日—2026年09月14日`）
- [ ] ② 总览首句「截至…」 —— 中文短格式，月日**不补零**（`截至2026年9月14日`）
- [ ] ③ 「本期周期：」＋各章周期标题 `## A—B` —— ISO 格式（`2026-09-14—2026-09-20`）
- [ ] ④ 页头「观察周期」 —— **不需手改**，自动读 ①
- [ ] ⑤ 页头「更新于」 —— **不需手改**，自动读内容源文件 mtime（且不得写进内容源）

勾完必须全部为「是」，否则不得提交：

- [ ] ① 与 ④ 逐字相同，② 等于 ① 的结束日，③ 是 ① 结束日所在自然周（周一—周日，`Asia/Shanghai`）。
- [ ] 新增一周内容时，①②③ 在同一轮一起推进（只加内容不改时间 = 页面显示旧周期）。
- [ ] 内容源中不出现「更新于」字样。
- [ ] `pnpm check` 通过（不一致会被下方不变量断言拦下）。

必须同时成立的不变量（由 `tests/governance.test.mjs` 自动校验，不一致时 `pnpm check` 失败）：

- 第 1 项的起始日不晚于结束日；
- 第 2 项与第 1 项**逐字相同**；
- 第 3 项的日期**等于**第 1 项的结束日；
- 「本期周期」＝ 第 1 项结束日所在的自然周（周一—周日，`Asia/Shanghai`），且结束日落在该区间内；
- 第 1 项的结束日不早于正文中最新周期标题的起始日（新增一周内容时必须连改第 1、3、4 项）；
- 内容源中**不得出现「更新于」**字样。

三个易踩的坑：

- **两种中文格式不一样**：第 1 项补零（`09月14日`）、第 3 项不补零（`9月14日`），字面不同，无法一次替换，必须分别改。
- **第 5 项是文件时间，不是内容里的日期**：只 touch 文件、不改内容，它也会变；内容改了却没重新构建，它不会变。所以**不能用它判断内容是否最新**——它只表示「这份页面是什么时候构建的」。内容新鲜度看第 1 项的结束日。
- **第 2 项取的是内容源里第一个中文长日期区间**：第 1 项必须仍是全文第一个 `YYYY年MM月DD日—YYYY年MM月DD日`，否则页头会显示别的日期（该情形会被上面第 2 条不变量拦下）。

## 5. 重点摘要

重点摘要使用固定七列表格：

```markdown
| 事件 | 类型 | 关键词 | 一句话影响判断 | 来源 | 发布时间 | 详细分析 |
|---|---|---|---|---|---|---|
| 示例事件 | 技术与模型 | ASR、评测 | 一句话判断 | 官方来源 | 2026-09-07 | [查看详情](#example-event) |
```

约束：

- 每行必须包含七列，不得缺列或交换顺序。
- `关键词` 使用顿号、中文逗号或英文逗号分隔。
- `发布时间` 使用 `YYYY-MM-DD`。
- `来源` 写可识别的机构或官方渠道；详细条目中尽量附一手链接。
- `详细分析` 使用 `[查看详情](#稳定锚点)`，指向正文中唯一的详细条目。
- 只有达到本期优先关注门槛的事件才进入该表。

## 6. 详细事件条目

详细条目至少应提供事实、变化、能力、业务和行动五类价值中的两类；重点事件至少提供三类。推荐字段：

```markdown
#### 事件名称 {#example-event}
情报维度：终端=电视大屏、机顶盒；能力=内容搜索与播放、任务编排；竞对=酷开；归因=体验问题、资源/商务问题；层级=L1-生存层
判断状态：持续跟踪
标签：#ASR #家庭场景

1. 事实与变化：……
2. 核心机制或能力：……
3. 证据与边界：……
4. 对 平台团队的影响：……
5. 建议动作：……
6. 来源：https://example.com
发布时间：2026-09-07
核验状态：已核验 / 待核验
```

字段可以按事件价值适度删减，但不得省略事实来源和时间边界。

### 6.1 竞争情报维度

第四至第七章的四级条目会被页面转换为可折叠情报卡片。对重点条目和需要进入多维筛选的条目，必须在标题下一行增加 `情报维度`：

```markdown
情报维度：终端=电视大屏、机顶盒；能力=ASR、内容搜索与播放；竞对=Amazon/Alexa；归因=体验问题、资源/商务问题；层级=L1-生存层
```

约束：

- 字段顺序固定为 `终端`、`能力`、`竞对`、`归因`、`层级`；没有竞对时可以省略 `竞对`，其他字段应尽量填写。
- 多值使用顿号 `、` 分隔，字段之间使用中文分号 `；`。
- `归因` 只使用 `能力问题`、`体验问题`、`资源/商务问题`、`交付问题`。尚不能归因时写 `待归因`，不得用“综合问题”回避责任边界。
- `层级` 只使用 `L1-生存层`、`L2-竞争层`、`L3-未来层` 或 `待分层`。
- `L1-生存层` 指招采准入、基础内容检索、EPG 融合、鉴权与播放闭环、多省交付等缺失即可能出局的能力。
- `L2-竞争层` 指自然打断、上下文、多意图、远场抗噪和失败恢复等形成可感知差异的体验。
- `L3-未来层` 指复杂任务编排、跨端记忆、视觉多模态和主动服务等长期壁垒候选，不替代 L1 问题。
- 同一业务现象可以有多个归因，但正文必须说明判断顺序和各自对应的行动团队。

同步脚本只对历史条目的终端、能力和竞对做受控关键词补标；归因和层级不自动推断，缺失时分别显示 `待归因` 和 `待分层`，用于暴露内容治理缺口。

事件标题使用四级标题，避免进入时间范围二级导航；重点摘要引用的事件必须追加 `{#稳定锚点}`。锚点仅使用小写英文字母、数字和连字符，一经发布不随标题措辞变化而修改。同步脚本会移除 `{#...}` 标记并把锚点写入网页标题。

第四至第七章在网页上默认只显示标题、结论摘要、竞争层级和归因标签，详细证据按需展开。编辑者仍应在 Markdown 中保留完整事实、证据边界和建议动作，不得为了页面简短删掉核验链路。

从富文本或内部文档复制内容后，提交前必须全文清理 `暂时无法在外部协作文档外展示此内容`、`[if !supportLists]`、`[endif]`、`mso-` 等占位符或样式残留。事件分析应使用“事件事实 + 分析”嵌套列表，不得把多个编号、短横线和“剖析”段落粘连在同一段中。

## 7. 公司内部进展

内部进展采用以下结构：

```markdown
八、公司内部进展

> 内容边界：本章为存量能力索引，能力状态以最新有效文档与实际接口行为为准。

**阅读说明**
**能力总览**
## 已有技术能力
### 语音合成（TTS）
#### 具体能力名称

```

> 二级标题不携带状态后缀：`（存量材料）` 等状态口径统一在章首「阅读说明」与「内容边界」中声明，避免同一状态在标题与正文重复出现、且不易随材料更新而修订。

每项内部能力建议记录：

- 信息来源；
- 确认日期；
- 责任团队；
- 当前阶段；
- 适用产品；
- 关键指标及测试条件；
- 依赖与风险；
- 下一步动作。

缺少当前有效内部依据时，必须标记“存量材料”。外部材料不能直接证明公司内部能力状态。

第八章页面会把三级标题显示为能力域，把四级标题显示为可展开的能力卡片。因此：

- `阅读说明` 以章首强调文本交代材料来源、阅读方式和状态边界，不新增标题锚点；
- `能力总览` 以章首强调文本和表格列出能力域、原始材料包含的能力和材料状态，不占用既有二级导航编号；
- `###` 只用于稳定的能力域；
- `####` 只用于单项具体能力；
- 具体能力的事实、版本、效果、限制和场景仍写在对应四级标题下，不写入 TSX 组件。


## 8. 变更本契约

新增字段或调整格式时，必须同步完成：

1. 更新本文件；
2. 在 Markdown 中提供真实示例；
3. 修改 `scripts/sync-content.mjs`；
4. 修改页面展示和样式；
5. 增加或更新自动测试；
6. 在实际发布后更新 `CHANGELOG.md`。

## 9. 存量章节与日更章节（2026-09-15）

内容分三层，更新频率与公开性不同，禁止互相覆盖：

| 层 | 载体 | 是否公开 | 更新频率 |
|---|---|---|---|
| raw 原始源 | `internal/技术能力清单.md`（列入 `.gitignore`） | 不公开 | 手动维护 |
| 整理版（存量章节） | `八、公司内部进展` | 公开 | 稳定，不随日更变化 |
| 日更章节 | 第四至第七章 | 公开 | 每日可能更新 |

- **存量章节**（第八章）：从 `internal/` 原始源整理而来，只在手动更新时重新生成；**日更流程不得改动**；
- **日更章节**（第四至第七章）：每日扫描可能新增条目；
- **总览**（第二章）：基于全部存量 + 本期新增周期性更新；
- 公开的整理版必须脱敏：内部资源标识、参数、错误码、接口地址、客户名只留在 `internal/` 原始源；
- 第八章状态口径为「状态：存量材料」，版本状态统一为 `当前`／`已废弃`／`在研`。
