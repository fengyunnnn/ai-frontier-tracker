# Markdown 内容契约

## 1. 适用范围

本契约约束 `content/行业动态追踪.md` 的可解析格式。内容编辑者可以增加事实和分析，但不得随意改变以下标题、字段和日期口径。

## 2. 固定一级章节

一级章节必须使用中文序号、顿号和固定名称，并保持唯一：

```markdown
一、文档说明
二、总览
三、本期重点摘要
四、行业动态
五、产品动态
六、技术革新
七、竞品与标杆公司动态
八、公司内部进展
```

如果确需增加、删除或改名，应先修改本契约，再修改同步脚本、页面导航和测试。

## 3. 章节内标题

```markdown
## 二级标题
### 三级标题
#### 具体条目或能力名称
```

- `##` 和 `###` 自动进入章节内导航。
- `####` 只作为正文小标题，不进入章节内导航。
- 同一章节内标题应语义清晰，不使用“其他”“补充”等无法长期识别的名称。

### 文档说明示例

```markdown
一、文档说明
## 文档目的
## 服务对象
## 内容覆盖
## 更新方式
## 覆盖时间
```

`## 内容覆盖` 说明报告的主线范围、双轨制（轨道 A 交互体验与 AI 前沿战略雷达／轨道 B 业务落地与产业约束雷达）与两条轨道的关系；`## 更新方式` 只保留日常扫描、周度整理、周期复盘、专题升级四项流程，不再夹带轨道说明。

### 周期章节示例

第四至第七章按照最新周期在前排列：

```markdown
## 2026-09-01—2026-09-07
## 2026-08-24—2026-08-30
```

## 4. 日期规则

- 单日日期：`YYYY-MM-DD`，例如 `2026-09-07`。
- 时间范围：`YYYY-MM-DD—YYYY-MM-DD`，中间使用中文长横线 `—`。
- 覆盖时间正文可以使用 `YYYY年MM月DD日—YYYY年MM月DD日`。
- 发现日期、媒体发布时间和事件发生日期不等同时，应明确区分。

## 5. 本期重点摘要

重点摘要使用固定七列表格：

```markdown
| 事件 | 类型 | 关键词 | 一句话影响判断 | 来源 | 发布时间 | 详细分析 |
|---|---|---|---|---|---|---|
| 示例事件 | 技术与模型 | ASR、评测 | 一句话判断 | 官方来源 | 2026-09-07 | [查看详情](#example-event) |
```

约束：

- 每行必须包含七列，不得缺列或交换顺序。
- `关键词` 使用顿号、中文逗号或英文逗号分隔。
- `发布时间` 使用 `YYYY-MM-DD`。
- `来源` 写可识别的机构或官方渠道；详细条目中尽量附一手链接。
- `详细分析` 使用 `[查看详情](#稳定锚点)`，指向正文中唯一的详细条目。
- 只有达到本期优先关注门槛的事件才进入该表。

## 6. 详细事件条目

详细条目至少应提供事实、变化、能力、业务和行动五类价值中的两类；重点事件至少提供三类。推荐字段：

```markdown
#### 事件名称 {#example-event}
情报维度：终端=电视大屏、机顶盒；能力=内容搜索与播放、任务编排；竞对=酷开；归因=体验问题、资源/商务问题；层级=L1-生存层
判断状态：持续跟踪
标签：#ASR #家庭场景

1. 事实与变化：……
2. 核心机制或能力：……
3. 证据与边界：……
4. 对 OS 平台部的影响：……
5. 建议动作：……
6. 来源：https://example.com
发布时间：2026-09-07
核验状态：已核验 / 待核验
```

字段可以按事件价值适度删减，但不得省略事实来源和时间边界。

### 6.1 竞争情报维度

第四至第七章的四级条目会被页面转换为可折叠情报卡片。对重点条目和需要进入多维筛选的条目，必须在标题下一行增加 `情报维度`：

```markdown
情报维度：终端=电视大屏、机顶盒；能力=ASR、内容搜索与播放；竞对=Amazon/Alexa；归因=体验问题、资源/商务问题；层级=L1-生存层
```

约束：

- 字段顺序固定为 `终端`、`能力`、`竞对`、`归因`、`层级`；没有竞对时可以省略 `竞对`，其他字段应尽量填写。
- 多值使用顿号 `、` 分隔，字段之间使用中文分号 `；`。
- `归因` 只使用 `能力问题`、`体验问题`、`资源/商务问题`、`交付问题`。尚不能归因时写 `待归因`，不得用“综合问题”回避责任边界。
- `层级` 只使用 `L1-生存层`、`L2-竞争层`、`L3-未来层` 或 `待分层`。
- `L1-生存层` 指招采准入、基础内容检索、EPG 融合、鉴权与播放闭环、多省交付等缺失即可能出局的能力。
- `L2-竞争层` 指自然打断、上下文、多意图、远场抗噪和失败恢复等形成可感知差异的体验。
- `L3-未来层` 指复杂任务编排、跨端记忆、视觉多模态和主动服务等长期壁垒候选，不替代 L1 问题。
- 同一业务现象可以有多个归因，但正文必须说明判断顺序和各自对应的行动团队。

同步脚本只对历史条目的终端、能力和竞对做受控关键词补标；归因和层级不自动推断，缺失时分别显示 `待归因` 和 `待分层`，用于暴露内容治理缺口。

事件标题使用四级标题，避免进入时间范围二级导航；重点摘要引用的事件必须追加 `{#稳定锚点}`。锚点仅使用小写英文字母、数字和连字符，一经发布不随标题措辞变化而修改。同步脚本会移除 `{#...}` 标记并把锚点写入网页标题。

第四至第七章在网页上默认只显示标题、结论摘要、竞争层级和归因标签，详细证据按需展开。编辑者仍应在 Markdown 中保留完整事实、证据边界和建议动作，不得为了页面简短删掉核验链路。

从富文本或内部文档复制内容后，提交前必须全文清理 `暂时无法在i讯飞文档外展示此内容`、`[if !supportLists]`、`[endif]`、`mso-` 等占位符或样式残留。事件分析应使用“事件事实 + 分析”嵌套列表，不得把多个编号、短横线和“剖析”段落粘连在同一段中。

## 7. 公司内部进展

内部进展采用以下结构：

```markdown
八、公司内部进展

> 内容边界：内部状态以当前有效材料和责任团队确认为准。

**阅读说明**
**能力总览**
## 已有技术能力
### 语音合成（TTS）
#### 具体能力名称

## 在研方向
```

> 二级标题不携带状态后缀：`（存量材料）`、`（待内部确认）` 等状态口径统一在章首「阅读说明」与「内容边界」中声明，避免同一状态在标题与正文重复出现、且不易随材料更新而修订。

每项内部能力建议记录：

- 信息来源；
- 确认日期；
- 责任团队；
- 当前阶段；
- 适用产品；
- 关键指标及测试条件；
- 依赖与风险；
- 下一步动作。

缺少当前有效内部依据时，必须标记“待内部确认”。外部材料不能直接证明公司内部能力状态。

第八章页面会把三级标题显示为能力域，把四级标题显示为可展开的能力卡片。因此：

- `阅读说明` 以章首强调文本交代材料来源、阅读方式和状态边界，不新增标题锚点；
- `能力总览` 以章首强调文本和表格列出能力域、原始材料包含的能力和材料状态，不占用既有二级导航编号；
- `###` 只用于稳定的能力域；
- `####` 只用于单项具体能力；
- 具体能力的事实、版本、效果、限制和场景仍写在对应四级标题下，不写入 TSX 组件。

## 8. 变更本契约

新增字段或调整格式时，必须同步完成：

1. 更新本文件；
2. 在 Markdown 中提供真实示例；
3. 修改 `scripts/sync-content.mjs`；
4. 修改页面展示和样式；
5. 增加或更新自动测试；
6. 在实际发布后更新 `CHANGELOG.md`。
