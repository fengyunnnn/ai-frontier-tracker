## 卡 A｜交互与用户研究类

### **Tinker Tales：儿童—AI 共创故事里的「提示框架」效应**

| 五行 | 内容 |
|---|---|
| **问题** | 在儿童与 AI **共创**（而非 AI 主导教学）的场景里，**对话设计本身**会不会改变儿童参与对话的方式？——现有研究多集中在「AI 主导的教学」情境，**共创情境下的对话设计如何塑造儿童—AI 对话，仍属未充分研究**（论文原话：*remains underexplored*） |
| **方法或产品机制** | **Tinker Tales** 有形对话系统：物理故事板 ＋ **NFC 嵌入式玩具**（角色／地点／物品／情绪）＋ 移动应用；通过**有形操作 ＋ 语音对话**两条通道做多模态交互。两个教育框架（**叙事发展**、**社会情感学习**）被**实例化为对话设计**，约束 agent 在**四个叙事阶段**里如何与儿童互动。研究设计：**家庭环境用户研究**，**两种对话设计条件**——差异在 agent **如何组织「展开（elaboration）」**，即**有／无教育脚手架** |
| **指标、样本或可用范围** | 样本：**10 名儿童（6—8 岁）**，居家研究，两条件对照。报告的结果变量是**儿童叙事贡献的「形式与一致性」**（form and consistency），属**质性／编码类**结果，**不是**时延、识别率、完成率这类工程指标。可用范围：论文为**同行评审**（SIGDIAL 2026；arXiv **2602.04109**，v1 2026-02-04，**v3 2026-09-11**，`cs.HC`／`cs.AI`），成熟度＝**实验** |
| **主要发现** | **提示框架（prompt framing）塑造了儿童叙事贡献的形式与一致性**，从而**结构化了他们参与共创对话的方式**（*prompt framing shapes the form and consistency of children's narrative contributions, structuring how they participate in co-creative dialogue with AI*）。配套机制主张：脚手架（scaffolding）支持**连贯的叙事推进**，同时**不削弱儿童的主体性（without diminishing children's agency）** |
| **证据边界与下一步验证** | ① **样本 10 人**、单一文化语境（Emory／CMU 团队、美国家庭），**非中文家庭、非电视大屏、非遥控器形态**，外推需谨慎；② 摘要层**未见效应量或统计检验**，结论为方向性表述；③ **不得引用第三方 AI 摘要里的「9/10 儿童」**——该数字出自 AI 生成的摘要页，非论文原文（见 `05` §6 **E-16**）；④ 下一步：读全文取**编码方案**与两条件的**差异量**，再判断「提示框架」是否可迁移为**大屏语音助手的引导话术**（如「要不要我接着讲？」），以及与方向 9（情绪语气）／10（主动交互与记忆）是否联动 |

**一句话版（供周报草稿参考，未收录）**：同行评审研究显示，agent 组织「展开」的提示框架会系统性改变儿童叙事贡献的形式与一致性——**同样的能力，换一套提问结构，产出就不一样**。

## 卡 B｜产品与开发者生态类

### **NVIDIA NemotronLabs VoiceChat 11B：把「等工具返回的沉默」变成可播报的交互状态**

| 五行 | 内容 |
|---|---|
| **问题** | 端到端全双工语音模型能否在**保留自然对话**（可打断、低延迟承接）的同时**执行工具调用**（查数据、下单），把工具执行期的**静默**变成**可设计的交互**？ |
| **方法或产品机制** | 单一统一模型做**流式语音理解 ＋ 语音生成**：Fast Conformer 语音编码 → **Nemotron Nano v2 9B** 骨干 → TTS 解码器；**另设一条独立输出通道预测工具调用脚本**。关键交互机制：**每个工具可预定义一段「on-hold」播报文本，模型一触发工具调用就先把这句话说出来**（把等待期显式化）。架构上不再需要 ASR→LLM→TTS 三段拼接与 API 交接 |
| **指标、样本或可用范围** | 参数 **11B**；**轮次延迟 ~450 ms**；**VoiceBench（开源全双工子集）排 #2**；**首个支持工具调用的开源全双工模型**；输入 16 kHz／输出 22.05 kHz；运行 **vLLM**，支持 A100／H100／H200／B100／B200／RTX-6000，**Linux**；发布日 **2026-08-03**；许可 **OpenMDW License 1.1**。可用范围：模型卡自述「**ready for research purposes only**」（成熟度＝**开发者可用，限研究**） |
| **主要发现** | 在开源阵营里，**全双工与工具调用首次被放进同一个模型**，且**把工具执行的等待期当作可播报的交互状态**而非静默。与同轮其他一手源指向同一方向：`node-webrtc-rust` 0.4.0（2026-06-02）的**语义打断**要求 STT **先识别出真实词**才停播（`bargeIn.requireSttPartial` 默认 true，咳嗽与纯音不触发）；LiveKit Agents 的打断 `mode` 默认 **`adaptive`**，并可在**误打断**后按 `false_interruption_timeout` 从原处续说。—— **打断与轮次不再是定时器问题，而是语义问题** |
| **证据边界与下一步验证** | ① 位置＝**原始（厂商模型卡）**，但指标为**厂商自报**，含 **VoiceBench 自榜位次**，**未见独立复现**；② **硬门槛与主业场景距离远**：需**数据中心级 GPU**＋Linux＋vLLM，**不能**直接推到机顶盒／端侧场景，**只能作为「云端能力上限」参照**；③「on-hold 播报」是**产品交互设计主张**，模型卡**未给用户研究证据**（不证明用户更喜欢）；④ 用途限制**明写为仅研究**，不得表述为「可上线能力」；⑤ 下一步：核 **VoiceBench 的评测口径与榜单快照日**、取第三方复现、并确认**是否有中文／方言能力说明** |

**一句话版（供周报草稿参考，未收录）**：开源侧出现首个「全双工＋工具调用」同体模型，并把工具等待期做成可播报状态；但限研究用途、需数据中心级 GPU。
