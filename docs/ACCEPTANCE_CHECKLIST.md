# 行业动态追踪端到端验收清单

> 文档状态：阶段 0 冻结版  
> 使用方法：阶段 1—7 每次验收时复制对应清单，填写运行编号、证据和结论。  
> 放行原则：所有阻断项必须勾选通过；不适用项必须说明原因，不能直接跳过。

## 1. 验收记录头

```markdown
- 运行/变更编号：
- 验收阶段：阶段 1 / 2 / 3 / 4 / 5 / 6 / 7
- 验收日期：
- 验收人：
- 目标分支：
- 目标文档：content/行业动态追踪.md
- 关联提交号：未提交 / <commit>
- 线上地址：未发布 / <url>
- 结论：通过 / 有条件通过 / 不通过
- 未通过项与下一步：
```

## 2. 总体放行规则

### 2.1 阻断项

出现以下任一情况不得进入发布：

- UI 必需字段不能追溯到 Input Contract；
- 重点摘要缺标题、影响判断、来源、发布时间或有效详情锚点；
- 正式条目缺事实来源或时间边界；
- 未核验信息被写成确定事实；
- 固定八个一级章节被意外修改；
- 历史稳定锚点被无理由删除或更换；
- `app/content.generated.ts`被手工编辑；
- Git diff 包含未授权、无法解释或异常删除的内容；
- `pnpm check`失败；
- GitHub Pages 部署失败或线上冒烟未通过，却准备宣称“已发布”。

### 2.2 允许带警告继续的事项

以下项目可以在风险明确、UI 有显式回退且不影响事实准确性时带警告继续：

- 非重点历史条目缺少竞对字段；
- 情报维度显示`待归因`或`待分层`；
- 章节没有二级或三级导航；
- 章节摘要尚处于兼容回退阶段，但目标 UI 已明确标记且阶段 2 有决策记录；
- 某些固定来源暂时无法访问，但不会改变本轮结论，并已记录盲区任务。

“有警告”不等于“可以静默忽略”。每条警告必须有责任阶段和后续动作。

## 3. 链路完整性标准

### 3.1 输入到输出完整性

- [ ] 用户原始指令已保存或可追溯。
- [ ] 时间窗口、时区、目标文档、受众和扫描模式已冻结。
- [ ] 环境预检已确认仓库、分支、远端和 Pages 发布方式。
- [ ] 外部扫描形成了来源覆盖记录，而不是直接进入内容写入。
- [ ] 原始线索已转换为符合 Input Contract 的结构化候选事件。
- [ ] Skill 输出符合 22 个事件内容字段、2 个流程决策和4个章节字段的约定。
- [ ] Skill 输出已转换为 Content Contract 规定的 Markdown 位置。
- [ ] Markdown 已通过同步脚本生成页面数据。
- [ ] 页面按 UI Contract 消费生成数据。
- [ ] 自动检查、构建、本地预览、Git 发布和线上冒烟各有独立状态。
- [ ] 最终发布回执包含提交号、部署状态、线上地址和遗留问题。

### 3.2 状态不混淆

- [ ] “扫描完成”没有被写成“内容已核验”。
- [ ] “内容已生成”没有被写成“内容已审核”。
- [ ] “构建通过”没有被写成“事实已核验”。
- [ ] “Git 提交完成”没有被写成“已推送”。
- [ ] “推送成功”没有被写成“Pages 已发布”。
- [ ] “Pages Workflow 成功”之后又执行了线上页面冒烟检查。

## 4. 字段闭环标准

目标：100%的 UI 必需字段能够沿“UI → Markdown → Skill → Input”反向追溯；任何缺口在进入下一层前可见。

### 4.1 重点摘要卡片

| 检查项 | UI | Markdown | Skill | Input | 验收 |
|---|---|---|---|---|---|
| 事件标题 | `event_title` | 七列表格第 1 列 | `event_title` | 主体+产品/主题+动作 | [ ] |
| 事件类型 | `event_type` | 第 2 列 | `event_type` | 事件性质和来源 | [ ] |
| 有序关键词 | `keywords_ordered` | 第 3 列 | `keywords_ordered` | 事实和候选五维信息 | [ ] |
| 影响判断 | `impact_summary` | 第 4 列 | `impact_summary` | 事实+变化+业务关联 | [ ] |
| 来源显示名 | `source_display` | 第 5 列 | `source_display` | 一手来源优先 | [ ] |
| 发布时间 | `publish_date` | 第 6 列 | `publish_date` | 官方日期/事件日期/发现日期 | [ ] |
| 详情锚点 | `stable_anchor` | 第 7 列及四级标题 | `stable_anchor` | 候选身份+去重结果 | [ ] |

重点摘要放行门槛：

- [ ] 每行恰好七列，顺序未改变。
- [ ] 发布时间为 `YYYY-MM-DD`。
- [ ] 每个详情锚点存在且全局唯一。
- [ ] 关键词顺序与 Skill 输出一致，UI 只做视觉限量展示。
- [ ] 影响判断不是官方宣传语的无标注复述。

### 4.2 情报卡片与详细条目

| 检查项 | Markdown 位置 | Skill 字段 | Input 依据 | 验收 |
|---|---|---|---|---|

情报条目放行门槛：

- [ ] 正式条目至少保留事实来源和时间边界。
- [ ] 重点条目至少覆盖事实、变化、能力、业务和行动中的三类价值。
- [ ] `待归因`、`待分层`和`待核验`如存在，均在页面或正文中显式可见。
- [ ] 来源、归因和竞争层级没有由 UI 临时推断。
- [ ] 详细正文没有为适应卡片而删除证据边界。

### 4.3 章节列表

- [ ] `section_id`可稳定生成且不重复。
- [ ] `section_numeral`与固定八章顺序一致。
- [ ] `section_title`与内容契约固定名称一致。
- [ ] `subsections`和`content_headings`对应实际 Markdown 标题。
- [ ] `full_body`完整来自内容源。
- [ ] `chapter_summary`已经结构化闭环；或已明确选择兼容回退并记录阶段 2 决策。
- [ ] 如果使用兼容回退，没有把正文首句误报为正式章节摘要。

### 4.4 搜索结果

- [ ] 搜索只基于生成后的章节标题、内容标题和正文。
- [ ] 搜索摘要只是原文截取，没有生成新事实。
- [ ] 有标题锚点时跳转到标题；没有时回退到章节根部。
- [ ] 空结果状态明确，不出现失效按钮。
- [ ] 搜索结果中的章节、标题和摘要均能追溯到 Markdown。

### 4.5 100%追溯判定

一次验收只有同时满足以下条件，才可标记“字段闭环通过”：

- [ ] 所有 UI 必需字段均出现在追溯表中。
- [ ] 每个必需字段都有唯一或受控的 Markdown 位置。
- [ ] 每个 Markdown 字段都有对应 Skill 输出字段。
- [ ] 每个 Skill 结论字段都能引用 Input Contract 的事实、来源或显式分析依据。
- [ ] 没有字段依赖无法解释的自由文本猜测。
- [ ] 已知缺口有明确回退、责任阶段和截止条件。

## 5. 人工介入点合理性标准

### 5.1 应保留人工判断

- [ ] 来源冲突和低置信度事实由人工裁决。
- [ ] 重点摘要准入由人工复核，至少在 0→1 阶段如此。
- [ ] 趋势增强、削弱和总览更新由人工复核。
- [ ] 客户决策链、问题归因和竞争层级由人工复核。
- [ ] 涉及内部能力、版本、指标、接口、责任人的内容标记“待内部确认”或已有有效依据。
- [ ] Markdown diff 在写入或发布前经过人工审核。
- [ ] 异常删除、Git 冲突和 Pages 失败由人工处理。
- [ ] 正式发布具有明确授权。

### 5.2 不应继续依赖人工搬运

- [ ] 时间窗口可由规则稳定计算。
- [ ] 七列表格字段不需要从多处手工复制。
- [ ] 表格与详细条目使用同一个稳定锚点。
- [ ] 同步、测试、Lint、类型检查和构建由命令统一执行。
- [ ] 自动生成文件不需要人工修正。
- [ ] 提交号、部署状态和线上地址可以进入统一回执。

人工介入合理的判定标准：人工精力集中于事实、判断、风险和授权；机械搬运、格式校验和重复命令逐步自动化。

## 6. 可落地性标准

### 6.1 项目与依赖

- [ ] 不引入新的前端框架或状态管理基础设施。
- [ ] 不引入第三方依赖来完成已有原生能力可以完成的工作。
- [ ] 改动遵循“契约 → 内容 → 同步 → 生成 → 页面 → 样式 → 测试”的方向。
- [ ] 页面组件没有写死具体行业事实。
- [ ] CSS 没有承载内容事实或业务规则。

### 6.2 生成链路

- [ ] `content/行业动态追踪.md`仍是唯一事实源。
- [ ] `scripts/sync-content.mjs`只在内容契约变化时修改。
- [ ] `app/content.generated.ts`含自动生成声明且未手改。
- [ ] `dist/`未被手工维护或纳入版本控制。
- [ ] 从 Markdown 重新同步后能得到一致的生成结构。

### 6.3 Git 与发布

- [ ] 当前仓库、分支和远端已经精确确认。
- [ ] 用户已有修改得到保留，没有被还原或覆盖。
- [ ] 提交只包含本轮授权范围内的文件。
- [ ] 推送目标确实会触发 GitHub Pages。
- [ ] Pages 部署完成后进行了线上冒烟。
- [ ] 发布回执没有夸大实际状态。

## 7. 阶段 1—7 可勾选验收清单

## 阶段 1：页面层目标落地

目标：让目标 UI Contract 成为真实页面消费者，不以当前旧实现否定目标契约。

- [ ] 重点摘要移动到目标信息流位置，并保持核心模块不丢失。
- [ ] 重点卡片只有一个明确的详细入口。
- [ ] 卡片展示日期、来源、类型、标题、影响和前两个标签。
- [ ] 多维筛选使用轻量原生交互，不引入额外基础设施。
- [ ] 未启用筛选时不渲染冗余情报结果流。
- [ ] 完整报告导航、章节阅读和搜索仍可使用。
- [ ] 缺失字段按 UI Contract 显示，不在组件中补造事实。
- [ ] 桌面端和移动端关键路径均可完成。
- [ ] 只修改计划授权的页面和样式文件。
- [ ] `pnpm check`通过。

阶段证据：页面截图或验收记录、相关 Git diff、检查日志。

## 阶段 2：存量内容适配与章节摘要决策

目标：让历史 Markdown 适合目标页面，并关闭章节摘要的产品决策缺口。

- [ ] 重点摘要仍为固定七列表格。
- [ ] 重点标题、影响摘要和关键词适合目标卡片规则。
- [ ] 所有重点事件均有唯一稳定锚点。
- [ ] 详细条目采用结论先行并保留完整证据。
- [ ] 五维情报字段满足现行内容 Schema。
- [ ] 历史锚点没有因标题改写而变化。
- [ ] 已明确决定：正式引入章节摘要 / 取消其必填要求 / 暂时兼容回退。
- [ ] 若正式引入，已明确 Markdown 唯一位置和迁移范围。
- [ ] 每批修改后均完成同步、检查和页面抽查。
- [ ] 没有手改生成文件。

阶段证据：内容审计表、批次 diff、章节摘要决策记录、检查日志。

## 阶段 3：Skill Output Contract 对齐

目标：让 Skill 稳定产出写入 Markdown 所需的全部内容字段和流程决策。

- [ ] 22 个事件内容字段均有明确输出位置。
- [ ] `highlight_eligible`包含布尔结果和理由。
- [ ] `duplicate_action`使用受控动作。
- [ ] 4 个章节级字段均明确输出或标记不适用。
- [ ] `event_title`与`detail_title`用途不同且不互相覆盖。
- [ ] `stable_anchor`符合格式并优先复用历史锚点。
- [ ] 事实、官方声称、独立证据、推断和建议被区分。
- [ ] 五维情报字段不依赖页面或解析器自动猜测。
- [ ] 低置信度内容保留`待核验`或进入候选池。
- [ ] 至少使用两组样例验证输出稳定性。

阶段证据：Skill 版本差异、输出样例、字段完整性检查结果。

## 阶段 4：Input Contract 输入包规范化

目标：让 Skill 接收结构化候选事件，而不是裸 URL 列表。

- [ ] 包级 7 个字段完整。
- [ ] 每条候选事件使用稳定 `candidate_id`。
- [ ] 官方发布时间、事件日期和发现日期明确区分。
- [ ] 一手来源与二手来源明确区分。
- [ ] 官方声称与已确认事实明确区分。
- [ ] 已知限制和待核验问题显式保留。
- [ ] `existing_matches`检查了已有标题和锚点。
- [ ] `possible_*`只作为候选，不冒充最终分类。
- [ ] 输入包中至少两条候选事件可完整追溯。
- [ ] 缺失值显式为空或`null`，不使用虚构值填满字段。

阶段证据：真实或脱敏输入包、字段审计结果、来源链接检查。

## 阶段 5：同步与契约校验补齐

目标：保证 Markdown 到页面数据的传输稳定，缺口能在发布前暴露。

- [ ] 先完成前端消费确认，再决定是否新增结构化字段。
- [ ] 未经触发条件，不修改解析器或 Schema。
- [ ] 如新增字段，已按内容契约→示例→脚本→页面→测试顺序修改。
- [ ] 旧 Markdown 在向后兼容范围内仍可同步。
- [ ] 缺失发布时间、来源、标题过长和标签超限可被报告。
- [ ] 软规则警告不阻断构建，结构硬错误继续阻断。
- [ ] 重点摘要锚点缺失或失效会阻断同步。
- [ ] 章节摘要若启用，缺失和解析失败可定位到具体章节。
- [ ] 生成结果能覆盖 UI 必需字段。
- [ ] `pnpm check`通过。

阶段证据：同步日志、警告样例、测试结果、生成字段抽查。

## 阶段 6：端到端试运行

目标：在正式发布前，用真实一周输入完整走通 13 步。

- [ ] 一句话已正确解析为周度扫描、整合和发布准备。
- [ ] 环境预检识别了现有工作区状态。
- [ ] 扫描形成覆盖记录、原始线索池和盲区任务。
- [ ] 输入包通过 Input Contract 检查。
- [ ] Skill 输出通过 Skill Output Contract 检查。
- [ ] Markdown diff 通过 Content Contract 检查。
- [ ] 人工完成事实、重点、归因和趋势审核。
- [ ] 同步、测试、Lint、类型检查和构建全部通过。
- [ ] 本地页面按 UI Contract 验收通过。
- [ ] 本轮停在发布前或发布到非正式验证目标，不误报正式上线。
- [ ] 运行记录包含每一步成功、失败和人工介入点。

阶段证据：完整运行记录、输入包、Skill 输出、diff、检查日志、本地验收记录。

## 阶段 7：GitHub Pages 正式发布与复盘

目标：在授权范围内完成真正上线，并能够证明线上版本正确。

- [ ] 发布前最后一次 Git diff 无异常删除或无关文件。
- [ ] 用户已有修改未被覆盖或混入提交。
- [ ] 提交信息能说明本周内容更新范围。
- [ ] 提交已推送到确认过的发布分支。
- [ ] GitHub Pages Workflow 成功完成。
- [ ] 线上页面加载成功，静态资源正常。
- [ ] 至少核对一条本周重点及其详细锚点。
- [ ] 线上内容与本次提交一致。
- [ ] 发布回执包含提交号、部署状态、线上地址和冒烟结果。
- [ ] 失败、警告和盲区已转为下一轮任务。
- [ ] 只有实际发布后才更新已发布记录。

阶段证据：提交号、Workflow 结果、线上 URL、冒烟记录、复盘结论。

## 8. 最终发布放行清单

每次正式发布前必须再次确认：

- [ ] 内容事实已核验，无法核验处已明确标记或排除。
- [ ] UI 必需字段100%可追溯。
- [ ] 重点摘要和详细条目锚点一一对应。
- [ ] 没有虚构公司内部进展、指标或接口状态。
- [ ] 没有异常删除和无关文件修改。
- [ ] `app/content.generated.ts`由同步脚本生成。
- [ ] `pnpm check`通过。
- [ ] 本地页面 P0 路径通过。
- [ ] 发布授权明确。
- [ ] 推送后继续等待并确认 Pages，而不是提前结束。

## 9. 验收结论模板
