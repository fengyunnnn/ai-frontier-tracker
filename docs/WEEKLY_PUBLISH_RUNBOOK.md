# 行业动态追踪每周整合与发布运行手册

> 文档状态：阶段 0 冻结版  
> 触发示例：`帮我整合本周重点事项并发布到 GitHub 静态网页`  
> 适用范围：每周扫描、内容增量整合、静态站生成、GitHub Pages 发布  
> 安全原则：一句话可以启动全流程，但不能跳过事实核验、差异审核、构建检查和发布结果确认。

## 1. 使用前提

执行本手册前必须满足：

- 四层字段要求以 `docs/END_TO_END_CONTRACT.md` 为准；
- 完成状态以 `docs/ACCEPTANCE_CHECKLIST.md` 为准；
- `content/行业动态追踪.md`是唯一事实源；
- `app/content.generated.ts`和`dist/`只允许由脚本生成；
- 不把构建成功等同于事实已核验或网页已发布；
- 不覆盖、不丢弃、不混入用户已有修改；
- 当前阶段如仍处于 0→1，发布前必须保留人工审核门。

## 2. 一句话触发的默认解析

触发语句：

> 帮我整合本周重点事项并发布到 GitHub 静态网页

默认解释：

| 指令片段 | 标准解释 | 不能默认的内容 |
|---|---|---|
| 本周 | `Asia/Shanghai`时区下，本周一 00:00 至调用时刻 | 不能把“最近七天”与“自然周”混为一谈 |
| 整合 | 读取既有文档、扫描、去重、核验、分类、生成最小增量修改 | 不等于重写整份报告 |
| 重点事项 | 达到重点准入门槛的少量事件 | 不等于把所有线索写入重点表 |
| 发布 | 更新内容源、同步生成、检查构建、提交推送、确认 Pages | 不等于仅完成 `git push` |
| GitHub 静态网页 | 当前仓库已经确认的 GitHub Pages 发布目标 | 不猜测分支、Workflow 或线上 URL |

趋势判断除本周窗口外，可以使用此前连续四周作为基线，但不得把基线内旧事件伪装成本周新增事件。

## 4. 分步执行说明

### 第 1 步：解析意图并冻结运行参数

输入：

- 用户原始指令；
- 当前日期与 `Asia/Shanghai`时区；
- 项目默认目标文档和受众背景。

处理：

1. 将“本周”解析为自然周起点至调用时刻；
2. 将运行模式设为“周度扫描 + 文档增量整合 + 发布”；
3. 将目标内容源设为 `content/行业动态追踪.md`；
4. 将受众设为 平台团队管理者、产品及相关研发协作方；
5. 记录本周窗口与连续四周趋势基线；
6. 不推断未定义的发布分支和 Pages URL，交由第 2 步确认。

输出：运行编号、扫描窗口、目标文档、受众、关注范围和发布意图。

成功：上述参数均唯一。失败：指令中的时间、范围或目标会导致两种实质不同的结果。

### 第 2 步：执行环境预检

输入：项目工作区、Git 状态、`package.json`、Pages Workflow。

处理：

1. 确认当前目录是目标仓库；
2. 读取当前分支、远端和工作区状态；
3. 识别用户已有修改，区分相关、无关和重叠修改；
4. 确认安装、同步、检查、构建命令；
5. 确认哪个分支推送会触发 GitHub Pages；
6. 确认当前凭据具备推送权限，但不在预检阶段推送。

输出：预检报告，至少包含仓库、分支、远端、脏文件、构建命令、发布触发条件。

成功：本轮变更可与已有修改安全区分。失败：存在可能覆盖用户内容的冲突、发布目标未知或权限不足。

### 第 3 步：扫描外部来源

输入：时间窗口、趋势基线、Skill V4 的来源优先级和覆盖范围。

处理：

1. 扫描固定来源和动态来源；
2. 聚合站点只作为线索入口，尽量回溯官方公告、产品文档、论文或代码仓库；
3. 记录每个线索的发现时间和页面时间；
4. 记录无法访问、没有更新或检索失败的来源；
5. 不在扫描阶段直接写 Markdown。

输出：原始线索池、覆盖记录和盲区说明。

成功：每条线索至少有来源入口，覆盖范围可审计。失败：关键来源缺失到足以改变“本周无重大事项”等结论。

### 第 4 步：组装 Input Contract

输入：原始线索池、现有 Markdown 中的标题和锚点。

处理：

1. 为每个候选事件生成 `candidate_id`；
2. 提取主体、产品/主题和动作；
3. 分离官方发布时间、事件日期和发现日期；
4. 分离一手来源、二手来源、官方声称和独立证据；
5. 列出已确认事实、已知限制和待核验问题；
6. 检查 `existing_matches`，为去重提供依据；
7. 组装包级字段和候选事件 22 个字段。

输出：符合 `END_TO_END_CONTRACT.md` 的结构化输入包。

成功：不是 URL 列表，且所有必需字段有值或显式空值。失败：事实只能从标题猜测、日期语义混乱或来源不可追溯。

### 第 5 步：执行 ai-frontier-tracker

输入：结构化输入包、现有内容源、周度模式。

处理：

1. 核验候选事实；
2. 与既有条目去重；
3. 为事件确定唯一主章节；
4. 输出事件标题、详细标题和稳定锚点；
5. 判断是否进入重点摘要；
6. 完成终端、能力、竞对、问题归因和竞争层级分类；
7. 分离事实、证据边界、业务影响和下一步动作；
8. 评估是否更新章节摘要或总览。

输出：22 个事件内容字段、2 个流程决策和4个章节字段。

成功：所有结论能追溯输入包。失败：使用输入中不存在的事实、把官方宣传当作独立证据或不说明不确定性。

### 第 6 步：校验 Skill 输出

输入：Skill 输出、端到端契约。

处理：

- 检查字段数量、类型、枚举、日期和锚点格式；
- 检查来源链接至少包含一条一手来源或说明为何缺失；
- 检查 `highlight_eligible`和`duplicate_action`；
- 检查重点条目是否具备更高的证据和业务价值；
- 检查章节级字段是否明确为更新、保持或不适用；
- 记录警告与阻断项，不进行静默修复。

输出：合格事件列表、待人工确认列表和排除列表。

成功：所有发布必需字段通过。失败：缺少标题、影响、日期、来源或锚点等关键字段。

### 第 7 步：生成 Markdown 修改提案

输入：合格 Skill 输出、Content Contract、现有 Markdown。

处理：

1. 依据 `duplicate_action`选择新增、更新、补来源或排除；
2. 依据 `report_section`和`period`定位插入位置；
3. 依据 `highlight_eligible`更新七列表格；
4. 使用同一 `stable_anchor`连接重点表格和详细条目；
5. 只在 `overview_update_action=更新`且证据达到门槛时提出总览修改；
6. 生成 diff，不直接覆盖整份文件。

输出：Markdown diff、拟新增/更新/删除统计和来源清单。

成功：只包含预期增量。失败：删除既有章节、改变固定标题、重复锚点或出现无关格式化。

### 第 8 步：人工审核发布内容

输入：Markdown diff、来源、证据边界、排除项和趋势判断。

必须审核：

- 事实是否被对应来源直接支持；
- 官方声称是否被标明；
- 低置信度内容是否保留“待核验”；
- 重点摘要是否真的值得占用管理者注意力；
- 问题归因是否指向正确的能力、体验、资源商务或交付环节；
- L1/L2/L3 判断是否有依据；
- 是否虚构内部能力、进展、接口状态或责任人；
- 是否存在异常删除、重复内容或历史锚点变化。

输出：审核通过、退回补证、降级为观察、排除或修订意见。

成功：审核者明确同意本轮内容进入内容源。失败：仍有影响结论的未解决问题。

### 第 9 步：更新唯一内容源

输入：审核通过的 Markdown diff。

处理：只更新 `content/行业动态追踪.md`，不得同步手工修改生成文件或页面组件。**同时必须刷新 4 处时间字段**——`## 覆盖时间` 正文、总览首个「截至」日期、重点摘要「本期周期：」、新增周期标题 `## A—B`（页头「更新于」由文件时间自动生成，不得手写）；清单与不变量见 `docs/CONTENT_SCHEMA.md` §4.1。

输出：更新后的 Markdown、精确 Git diff，以及时间字段同步核对结果。

成功：实际 diff 与审核提案一致，且 4 处时间字段自洽。失败：出现未授权文件、整篇换行或格式重写、旧锚点消失、时间字段互相矛盾。

### 第 10 步：同步生成数据

输入：更新后的 Markdown、`scripts/sync-content.mjs`。

处理：执行项目现有内容同步命令，覆盖生成 `app/content.generated.ts`。

输出：新的生成数据和同步日志。

成功：脚本正常结束，重点摘要全部指向存在的锚点。失败：解析异常、字段错位或重点链接失效。

### 第 11 步：检查、构建和本地验收

输入：所有本轮源文件和生成数据。

处理：

1. 运行 `pnpm check`；
2. 确认测试、Lint、TypeScript 和生产构建通过；
3. 本地预览目标页面；
4. 按 UI Contract 检查重点卡片、情报卡片、章节列表和搜索结果；
5. 检查桌面端、移动端、锚点、来源链接和回退状态；
6. 确认时间字段自洽（`pnpm check` 已包含该断言，见 `docs/CONTENT_SCHEMA.md` §4.1）。

输出：工程检查报告和 UI 验收记录。

成功：自动检查全通过，P0 页面字段和路径正确。失败：任一自动检查失败，或必需字段在页面不可见/跳转错误。

### 第 12 步：提交、推送并等待部署

输入：审核和验收通过的变更、发布授权。

处理：

1. 再次检查 Git diff；
2. 精确暂存本轮文件，不使用可能混入无关内容的广泛暂存；
3. 创建可追溯提交；
4. 推送到已经确认的发布分支；
5. 等待 GitHub Pages Workflow 完成；
6. 记录提交号和部署结果。

输出：提交号、远端分支、Workflow/Pages 状态。

成功：提交范围正确、推送成功、部署成功。失败：无权限、远端冲突、Workflow 失败或提交含无关修改。

### 第 13 步：线上冒烟检查与发布回执

输入：线上地址、提交号、部署结果。

处理：

- 打开线上页面；
- 核对本周新增重点标题和至少一个详细条目；
- 检查重点卡片到详细锚点；
- 检查静态资源加载；
- 检查页面显示版本与本次提交一致；
- 记录未阻断发布的警告和下一步任务。

输出：发布回执。

回执至少包含：

```text
运行编号：<run-id>
扫描窗口：<start>—<end>
新增/更新/排除：<数量>
内容审核：通过/未通过
工程检查：通过/未通过
提交号：<commit>
Pages 状态：成功/失败/未知
线上地址：<url>
线上冒烟：通过/未通过
遗留问题：<列表>
```

成功：线上实际显示本轮内容。失败：只完成推送但部署未知、页面仍显示旧内容或关键链接失效。

## 5. 人工介入点清单

### 5.1 0→1 阶段必须人工

- 来源冲突或低置信度事实的裁决；
- 重点摘要准入；
- 趋势增强、削弱或总览变化；
- 客户决策链、问题归因和业务影响判断；
- 涉及内部能力、版本、指标、接口和责任人的内容；
- Markdown diff 的最终内容审核；
- 本地页面的视觉与语义确认；
- 发布授权及异常处理。

### 5.2 可自动化但必须保留失败停止

- 时间窗口计算；
- Git 和项目环境只读预检；
- 来源扫描与覆盖记录；
- 输入包结构检查；
- 枚举、日期和锚点格式检查；
- Markdown diff 生成；
- 同步、测试、Lint、类型检查和构建；
- 精确提交和推送；
- Pages 状态查询及线上冒烟。

## 6. 失败处理路径

### 6.1 脏工作区

```text
发现未提交修改
  ├─ 与本轮无关且不重叠 → 保留，不纳入本轮暂存；继续
  ├─ 与本轮文件相同但区域不重叠 → 明确标记，逐块审查；谨慎继续
  └─ 与本轮修改重叠或来源不明 → 停止，向用户说明冲突位置
```

禁止行为：

- 不执行 `git reset --hard`；
- 不使用还原命令丢弃用户修改；
- 不为方便发布而静默 `stash`用户内容；
- 不使用笼统的 `git add .`混入无关文件。

恢复条件：重叠修改已由用户确认处理方式，或本轮修改可被安全隔离。

### 6.2 Git 远端冲突

```text
推送被拒绝
  → 读取远端变化
  → 判断是否存在同文件冲突
  → 无冲突时采用非破坏性整合
  → 有冲突时停止并人工合并
  → 重新运行同步、检查、构建和页面验收
  → 再次推送
```

禁止强制推送覆盖远端历史，除非用户明确要求且目标已精确确认。

### 6.3 低置信度或证据不足

```text
关键事实无一手来源
  ├─ 可找到其他可靠来源 → 补证后重新核验
  ├─ 仅有官方声称 → 明确标注“官方表述”，降低结论强度
  ├─ 仅有二手线索 → 留在原始线索池或待处理候选池
  └─ 影响重大且无法核验 → 不发布，进入盲区任务
```

`待核验`不是把无依据内容发布为事实的许可证。

### 6.4 异常删除或大面积重写

出现以下任一情况立即停止：

- 固定八个一级章节被删除、改名或换序；
- 历史稳定锚点消失或改变；
- 本周增量任务删除历史周期或大量正文；
- diff 出现与目标无关的全文件换行、编码或格式变化；
- 重点摘要表行被批量删除但没有明确去重或纠错理由；
- 自动生成文件以外的代码或内容被意外修改。

处理方式：定位产生异常差异的步骤，重新从审核通过的 Markdown diff 开始；不得用生成文件反向修补内容源。

### 6.5 同步或构建失败

排查顺序：

1. 检查 Markdown 固定章节、七列表格和锚点；
2. 检查日期格式和情报维度行；
3. 检查同步脚本错误信息；
4. 检查生成数据是否由最新 Markdown 生成；
5. 分别定位测试、Lint、TypeScript 或 Vite 构建失败；
6. 修复源文件后重新执行完整检查。

禁止手改 `app/content.generated.ts`绕过失败。

### 6.6 Pages 部署或线上检查失败

```text
Git 推送成功但网页未更新
  → 检查 Workflow 是否启动
  → 检查 Workflow 构建和部署步骤
  → 核对发布分支与 Pages 配置
  → 核对提交号与线上版本
  → 检查静态资源 base path 和缓存
  → 修复后重新构建与发布
```

在 Pages 状态未知或线上冒烟未通过时，回执只能写“推送成功、发布未确认”，不能写“已发布”。

## 7. 运行产物与留痕

每次完整运行理论上应保留：

| 产物 | 作用 | 0→1 允许形式 |
|---|---|---|
| 运行参数 | 冻结本周范围和目标 | 审核记录或运行日志 |
| 覆盖记录 | 说明查过什么、缺什么 | 扫描日志 |
| Input Contract | 保存候选事件和原始证据 | JSON/YAML 或结构化 Markdown |
| Skill 输出 | 保存入选、排除、待核验及判断 | 结构化结果 |
| Markdown diff | 发布前审核对象 | Git diff |
| 工程检查结果 | 证明可生成和构建 | 命令日志 |
| 发布回执 | 证明远端和线上状态 | 提交号、URL、状态和冒烟结果 |

是否将这些产物长期提交进仓库，应在阶段 3—6 决定；本文不自动引入新的数据目录。

## 8. 文档使用说明

- **核心价值：** 把“一句话”拆成可执行、可停止、可审核和可证明上线的 13 步标准流程。
- **与另外两份文档的关系：** 本手册执行 `END_TO_END_CONTRACT.md`定义的字段接口，并用 `ACCEPTANCE_CHECKLIST.md`作为每步和每阶段的放行门槛。
- **阶段 1—7 引用方式：** 阶段 1—5 分别引用对应字段和检查步骤，阶段 6 按 13 步进行完整试运行，阶段 7 严格执行第 12—13 步并生成发布回执。
